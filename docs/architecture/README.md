# 아키텍처 문서

[`../../README.md`](../../README.md)의 **아키텍처** 섹션이 한 장으로 요약한 흐름을, 처음 보는
사람이 따라갈 수 있도록 항목별로 펼친 문서들입니다.

옆 디렉터리와 역할이 다릅니다.

- **여기(`architecture/`)** — **지금 어떻게 동작하는가.** 정상 흐름과 분기를 그림으로 설명합니다.
  코드를 처음 여는 사람이 "어느 파일부터 보면 되는지" 찾는 데 씁니다.
- [**`../troubleshooting/`**](../troubleshooting/) — **무엇이 잘못됐고 왜 그렇게 고쳤는가.**
  겪은 장애와 내린 판단의 기록입니다.
- [**`../refactor/`**](../refactor/) — **아직 하지 않은 일.** 알고는 있지만 손대지 않은 것과,
  손대지 않기로 결정한 것입니다.
- [**`../benchmark/`**](../benchmark/) — **재 본 결과.** 어떤 도구로 어떤 조건에서 쟀는지와,
  그 숫자가 말하지 않는 것입니다.

같은 주제를 양쪽에서 다룰 수 있습니다. SQS가 그렇습니다 — 흐름은 여기, 경합 사고와 브로커 선택은
저쪽입니다. 서로 링크로 잇되 설명을 되풀이하지 않는 것이 원칙입니다.

## 문서 규약

`../troubleshooting/README.md`와 같은 규약을 씁니다.

- 파일명은 **영문 kebab-case**. 한글 파일명은 URL 인코딩되어 링크가 읽기 어려워집니다.
  트러블슈팅과 달리 **번호는 붙이지 않습니다** — 사건 순서가 아니라 주제별 문서이기 때문입니다.
- 코드 인용은 5~15줄로 자르고 전체는 파일 링크로 넘깁니다. 문서가 코드 사본이 되면 금방 낡습니다.
- **라인 번호를 본문에 박지 않습니다.** 파일명과 메서드명으로 가리켜, 코드가 움직여도 문서가
  틀리지 않게 합니다.
- 다이어그램은 **순서나 분기가 핵심인 흐름**일 때만 그립니다. 이미 다른 문서에 같은 그림이 있으면
  새로 그리지 않고 링크합니다.
