# 02. SQS 멱등성 정합성 측정 — 중복 소비 하에서 데이터가 몇 건 남는가

> 주장 · **"중복 소비 방지를 위한 분산 큐(SQS) 멱등성 전략 적용 — 애플리케이션 레벨 멱등성 검증으로
> 인프라 교체 없이 동시성 문제 해결, 추가 비용 없이 분산 환경 데이터 정합성 100% 확보"**
> 관련 판단 · [트러블슈팅 03 — SQS 콜백 경합 조건](../troubleshooting/03-sqs-callback-race-condition.md) ·

> [아키텍처 — SQS 메시지 흐름](../architecture/sqs-message-flow.md)

## 1. 이 문서가 있는 이유

"정합성 100%"는 **정의 없이는 아무 뜻도 없는 문장**입니다. 무엇이 몇 건이어야 100%인지가 정해지지
않으면, 실패한 측정도 100%로 보고할 수 있습니다.

그리고 이 주장을 뒷받침하던 것은 **Mockito 스텁 위의 단위 테스트뿐이었습니다.**
[`AiNotificationServiceTest`](../../src/test/java/com/serverbe/application/service/AiNotificationServiceTest.java)는
`findByIdForUpdate`가 반환하도록 시킨 상태를 보고 분기가 갈라지는지를 확인합니다. 그것으로
알 수 있는 것은 **"우리가 짠 if 문이 의도대로 갈라진다"**까지입니다. 정작 주장의 핵심인 두 가지는
증명되지 않습니다.

- `SELECT ... FOR UPDATE`가 **동시에 들어온 두 스레드를 정말 직렬화하는가** — Mockito는 락을
  걸지 않습니다. 이 질문은 **진짜 MySQL의 행 락** 위에서만 답이 나옵니다.
- SQS의 **at-least-once 중복 전달이 정말 걸러지는가** — 스텁 호출은 중복 전달이 아닙니다.
  이 질문은 **진짜 큐**가 같은 메시지를 다시 줘야 답이 나옵니다.

그래서 스텁을 걷어내고 **실제 MySQL·실제 큐 위에서 재는** 측정을 따로 만들었습니다.

## 2. 무엇을 재는가 — 정합성의 정의

이 측정에서 **"정합성 100%"는 세 조건이 동시에 성립하는 것**을 뜻합니다. 하나라도 어긋나면
100%가 아닙니다.

| # | 조건 | 관측 방법 |
| --- | --- | --- |
| 1 | **중복 없음** — 등록된 러닝 아트 수가 서로 다른 작업 수와 같다 | `SELECT COUNT(*) FROM running_arts WHERE user_id = ?` |
| 2 | **유실 없음** — 전달한 메시지가 전부 소비되어 큐가 비었다 | `ApproximateNumberOfMessages` + `...NotVisible` == 0 |
| 3 | **오탐 없음** — 중복이 실패로 처리되지 않았다 | 종결 상태가 `FAILED`인 작업 수 == 0 |

```
정합성(%) = (1 − |실제 등록 건수 − 기대 등록 건수| / 기대 등록 건수) × 100
```

조건 2가 특히 중요합니다. **이것이 없으면 착시가 생깁니다.** 100건을 보냈는데 20건만 도착한
시점에 세면 등록도 20건이라 정합성이 맞아 보입니다. 나머지 80건이 아직 오지 않았을 뿐인데
말입니다. 그래서 테스트는 **큐가 완전히 빌 때까지 기다린 다음** 셉니다.

여기에 하나를 더 붙였습니다. **결과가 흔들리지 않고 유지되는지 10초 동안 더 지켜봅니다.**
뒤늦은 중복은 늦게 도착하고, 정합성은 깨진다면 늦게 깨집니다.

## 3. 무슨 도구로 재는가

| 역할 | 도구 | 이 선택의 이유 |
| --- | --- | --- |
| 큐 | **LocalStack 3.4** (SQS) — Testcontainers | 실제 at-least-once 전달과 가시성 타임아웃 재전달이 필요하다. 인메모리 가짜 큐로는 재전달을 흉내 낼 수 없다 |
| DB | **MySQL 8.0** — Testcontainers | `SELECT ... FOR UPDATE`의 행 락이 측정 대상이다. H2로는 InnoDB의 락 동작을 잴 수 없다 |
| 캐시 | **Redis 7** — Testcontainers | 측정 대상은 아니지만 컨텍스트 기동에 필요하다 |
| 실행 | JUnit 5 + Spring Boot Test (`local` 프로파일) | 상용과 같은 리스너·유스케이스·트랜잭션 경계를 그대로 태운다 |
| 대기 | **Awaitility** | SQS 소비는 폴링 스레드에서 일어나 완료 시점을 테스트가 알 수 없다. `sleep`으로 때려 맞히면 그 값이 곧 측정 조건이 된다 |

**왜 JMeter가 아닌가** — 01번 문서와 달리 이 측정의 부하는 HTTP가 아니라 **큐 메시지**입니다.
JMeter로도 SQS에 넣을 수는 있지만, 그러면 정작 확인해야 할 DB 최종 상태를 도구 밖에서 따로 세야
합니다. 전달·소비·검증을 한 프로세스 안에 두면 **"큐가 비었다"와 "행이 몇 개다"를 같은 시점에서
관측**할 수 있고, 이 측정에서는 그 동시성이 결과의 신뢰도를 좌우합니다.

**LocalStack은 실제 AWS SQS가 아닙니다.** 이 한계는 §7에 적었습니다.

## 4. 측정 조건

| 항목 | 값 | 이 값을 고른 이유 |
| --- | --- | --- |
| 서로 다른 작업 수 | **20** | 한 건만 재면 "우연히 직렬화됐다"를 배제하지 못한다 |
| 작업당 중복 전달 | **5회** | at-least-once의 현실적인 재전달 폭을 넘어서는 값. 총 **100건** 전달 |
| 전송 순서 | **셔플 후 병렬 전송** | 작업별로 몰아 보내면 같은 행을 노리는 사본들이 시간상 떨어져 도착해, **정작 검증하려던 락 경합이 일어나지 않는다** |
| 큐 가시성 타임아웃 | **5초** (운영 기본값은 30초) | 짧을수록 재전달이 잦아져 **측정이 더 불리해진다.** 유리한 쪽으로 조건을 고르지 않기 위한 선택 |
| 리스너 동시성 | Spring Cloud AWS 기본값 | 상용과 다른 값을 주면 그 값이 결과의 일부가 된다 |
| 초기 작업 상태 | 시나리오 1은 `PROCESSING`, 시나리오 2는 `PENDING` | 두 시나리오가 각각 트러블슈팅 03의 (b)와 (a)에 대응한다 |
| 안정성 관찰 창 | **10초** | 결과가 유지되는지 확인. 뒤늦은 중복은 늦게 온다 |

### 두 시나리오

**시나리오 1 — 중복 전달 (트러블슈팅 03의 증상 (b))**
`PROCESSING` 상태 작업 20건에 대해 완료 알림을 5번씩, 순서를 섞어 병렬로 보냅니다.
기대: 러닝 아트 **정확히 20건**, 작업마다 서로 다른 `result_art_id` 1건씩, `FAILED` 0건.

**시나리오 2 — PENDING 선착 콜백 (증상 (a))**
`PENDING` 상태 작업에 완료 알림을 먼저 보냅니다. 리스너는 예외를 던지고 큐는 재전달을 반복합니다.
이 구간 동안 **아무 결과도 만들어지면 안 됩니다** — 실패로 확정하는 것도, 미리 등록하는 것도
오답입니다. 그다음 상태를 `PROCESSING`으로 바꿔(요청 스레드가 뒤늦게 저장을 마친 상황) 재시도가
성공하는지, 그리고 **여러 번 재전달됐는데도 등록은 한 번뿐인지**를 확인합니다.

시나리오 2가 곧 **"추가 비용 없이"**의 근거입니다. 재시도 코드도, `sleep`도, 별도 스케줄러도 없이
**SQS가 이미 갖고 있는 가시성 타임아웃**만으로 복구된다는 것을 보이는 것이 이 시나리오의 목적입니다.

## 5. 재현 절차

**필요한 것** — Docker Desktop, 저장소 루트의 `.env`. (컨테이너는 테스트가 직접 띄우므로
로컬에 MySQL·Redis를 깔아 둘 필요는 없습니다.)

```powershell
.\gradlew integrationTest --tests "*SqsIdempotencyConsistencyTest" --info
```

첫 실행은 이미지 세 개(`mysql:8.0`, `redis:7-alpine`, `localstack/localstack:3.4`)를 받느라
몇 분 걸립니다.

표에 옮길 값은 테스트가 표준 출력으로 남깁니다.

```
[SQS 멱등성 측정] 시나리오=중복 전달 | 전달=100건 | 기대 등록=20건 | 실제 등록=?건 | 정합성=?%
```

**멱등성이 정말 동작하는지 눈으로 보고 싶다면** `--info` 로그에서 다음 줄을 찾으십시오.
중복 사본이 락을 기다렸다가 종결 상태를 보고 물러난 흔적입니다.

```
[AI Notification] Task ... 는 이미 종결된 작업입니다(현재 상태: COMPLETED). 중복/지연 메시지로 판단하여 재처리하지 않습니다.
```

시나리오 2에서는 재전달마다 다음 줄이 남습니다. `ERROR`가 아니라 `WARN`인 것도 의도된 구분입니다
— 이것은 장애가 아니라 정상 흐름의 일부입니다.

```
[AI Notification] 비동기 경합 조건(Race Condition) 발생 - Task [...] 가 아직 PENDING 상태입니다.
```

## 6. 측정 결과

**3회 연속 실행** · 2026-09-03 · Intel Core i5-11400 (6C/12T) · 32GB RAM · Windows 10 Pro ·
Docker 29.7.2 · `localstack/localstack:3.4` · `mysql:8.0` · `redis:7-alpine` ·
JDK 17 (Corretto 17.0.12) · 1회차 소요 1분 53초

| 시나리오 | 전달 | 기대 등록 | 실제 등록 (1·2·3회차) | 잔여 메시지 | `FAILED` | 정합성 |
| --- | --- | --- | --- | --- | --- | --- |
| 1. 중복 전달 (20 × 5) | 100건 | 20건 | **20 / 20 / 20건** | 0 | 0 | **100.00%** |
| 2. PENDING 선착 콜백 | 1건 + 재전달 | 1건 | **1 / 1 / 1건** | 0 | 0 | **100.00%** |

테스트가 남긴 원문입니다(3회차 모두 같은 줄이 나왔습니다).

```
[SQS 멱등성 측정] 시나리오=중복 전달 | 전달=100건 | 기대 등록=20건 | 실제 등록=20건 | 정합성=100.00%
[SQS 멱등성 측정] 시나리오=PENDING 선착 콜백 | 전달=1건 | 기대 등록=1건 | 실제 등록=1건 | 정합성=100.00%
```

**이 수치가 뜻하는 것을 좁혀서 말하면** — 100건을 흘려 넣고 큐가 완전히 빌 때까지 기다린 뒤에도
등록은 20건이었고, 그 상태가 10초 동안 흔들리지 않았습니다. 중복 80건은 실패가 아니라 **멱등
스킵**으로 처리되어 `FAILED`가 하나도 없습니다. 시나리오 2는 `PENDING`에 먼저 도착한 콜백이
실패로 확정되지도, 유실되지도 않고 재전달을 거쳐 **정확히 한 번** 처리됐습니다.

## 7. 이 측정이 말하지 않는 것

- **LocalStack은 실제 AWS SQS가 아닙니다.** 가시성 타임아웃과 at-least-once 전달의 **의미**는
  같지만, 리전 간 지연이나 실제 서비스의 중복 발생 빈도까지 재현하지는 않습니다. 이 측정이
  보이는 것은 "중복이 오면 우리 코드가 걸러 낸다"이지, "실제 SQS에서 중복이 얼마나 오는가"가
  아닙니다.
- **100%는 이 조건에서의 관측이지 증명이 아닙니다.** 20작업 × 5중복을 **3회** 돌려 한 번도 깨지지
  않았다는 뜻이며, 모든 인터리빙에 대한 보장이 아닙니다. 보장의 최종 근거는 측정이 아니라
  **DB 행 락의 의미론**입니다. 측정은 그 의미론이 우리 코드에서 실제로 작동하는지를 확인할 뿐입니다.
- **`maxReceiveCount`와 DLQ는 범위 밖입니다.** 시나리오 2는 재전달을 무한히 허용하는 큐에서
  돌립니다. `PENDING` 재시도가 반복될 때 DLQ를 오염시키지 않는 임계값이 얼마인지는
  [트러블슈팅 03 §7](../troubleshooting/03-sqs-callback-race-condition.md#7-남은-과제)에
  남은 과제로 걸려 있습니다.
- **S3 정리는 세지 않습니다.** 멱등 스킵 경로는 뒤늦게 도착한 결과물을 지우기도 하는데
  (`cleanUpResourcesAfterCommit`), `local` 프로파일에서는 S3가 목이라 삭제 호출 수를 세는 것이
  의미가 없습니다. 이 측정은 **DB 정합성**만 다룹니다.
- **처리 시간은 재지 않습니다.** 중복 100건을 소비하는 데 걸린 시간은 락 경합에 좌우되지만,
  이 측정의 관심사는 처리량이 아니라 **최종 상태의 정확성**입니다.
