## 1. 이 문서가 있는 이유

[01번 문서](01-thread-occupancy.md)는 **동시 100 · 정상 상태 60초**를 쟀습니다. 그 측정이 보인 것은
하나입니다 — 같은 처리량을 내는 데 동기 경로는 워커 101개를, 논블로킹 경로는 2개를 썼다.

그리고 01번 문서는 §7에서 **스스로 두 개의 구멍을 적어 두었습니다.**

> "동시 100은 아직 어느 쪽도 한계가 아닙니다. (…) 이 측정이 보이는 것은 같은 처리량을 내는 데
> 워커를 얼마나 쓰는가이지, 각 방식의 한계 처리량이 아닙니다."

60초라는 길이에도 같은 문제가 있습니다. **커넥션이 반납되지 않고 쌓이는 종류의 문제는 60초에
보이지 않습니다.** 워커 점유가 낮다는 것과 오래 켜 둬도 안전하다는 것은 다른 이야기인데, 01번
측정은 앞의 것만 답합니다.

이 문서는 그 두 구멍을 축으로 삼아 다시 잽니다.

| 축 | 01번 | 이 문서 |
| --- | --- | --- |
| 동시 사용자 | 100 | **100 · 300 · 500** (각각 따로) |
| 지속 시간 | 정상 상태 60초 | **정상 상태 10분** (ramp-up 이후 처음부터 끝까지 부하 유지) |
| 관측 | 워커 점유 · 처리량 · 지연 | 위 전부 + **힙 · 커넥션 풀 · 시간대별 추이** |

**측정 대상은 01번과 같은 세 경로 그대로입니다.** 새로 만든 엔드포인트는 없습니다.

## 2. 무엇을 재는가 — 지표의 정의

워커 점유의 정의는 01번과 같습니다. 비교 가능해야 하기 때문입니다.

```
스레드 사용률(%) = tomcat.threads.busy / tomcat.threads.config.max × 100     (max = 200)
```

이번에 추가한 세 지표는 정의를 새로 못 박아야 합니다.

| 지표 | 정의 | 왜 이 정의인가 |
| --- | --- | --- |
| **힙 사용량** | `jvm.memory.used{area=heap}` (MB) | 요청받은 "힙 메모리". 다만 아래 이유로 이 값만으로는 누수를 판정하지 않는다 |
| **live set** | `jvm.gc.live.data.size` (MB) | **누수 판정의 본선 지표.** 힙 used 는 GC 주기에 따라 톱니로 오르내려서, 시작과 끝 두 점만 비교하면 "GC 직후에 쟀는가"가 결론을 바꾼다. live set 은 old 세대 수집 직후 살아남은 양이라 그 잡음이 없다 |
| **커넥션 풀 사용량** | 앱 컨테이너에서 **스텁(8080)으로 나가는 ESTABLISHED 소켓 수**. `/proc/net/tcp`·`tcp6` 를 직접 센다 | 경로마다 클라이언트가 달라(JDK `HttpClient` vs Reactor Netty) Micrometer 풀 게이지로는 세 경로를 같은 잣대에 놓을 수 없다. 소켓은 클라이언트가 무엇이든 같은 뜻이다 |
| **에러율** | JMeter 샘플 중 `success != true` 의 비율. 응답 코드 200 assertion 을 포함한다 | 타임아웃으로 조기 반납된 요청이 "빠른 응답"으로 집계되는 것을 막는다 |

**"커넥션 풀 사용량"을 소켓 수로 정의한 대가가 하나 있습니다** — 획득 대기(pending) 건수는 직접
보이지 않습니다. 풀이 천장에 닿았는지는 소켓 수가 상한에 붙고 **지연이 함께 올라가는 것**으로
판정합니다. §6에서 실제로 그 장면이 나옵니다.

## 3. 무슨 도구로 재는가

01번과 같은 구성이되, 샘플러를 **둘로 나눴습니다.**

| 역할 | 도구 | 간격 | 산출물 |
| --- | --- | --- | --- |
| 부하 생성 | Apache JMeter 5.6.3 (non-GUI) | — | `results.csv` |
| 외부 API 대역 | WireMock 3.9.1 (고정 지연 500ms) | — | — |
| 워커 점유 관측 | Actuator `tomcat.threads.busy` | **250ms** | `metrics.csv` |
| 자원 관측 | Actuator(힙·live set·Hikari·JVM 스레드) + `/proc/net/tcp` + 호스트 CPU | **5초** | `resources.csv` |
| 집계 | [`summarize.ps1`](../../perf/thread-occupancy/summarize.ps1) | — | `summary.csv` · `timeseries.csv` |
| 12회차 진행 | [`run-matrix.ps1`](../../perf/thread-occupancy/run-matrix.ps1) | — | `matrix-log.csv` |

**샘플러를 왜 나눴는가** — 샘플러의 요청도 톰캣 워커를 하나 씁니다. 01번 측정에서 동기 경로의
`busy` 가 100 이 아니라 이따금 101 로 찍힌 것이 그 흔적입니다. 이번에는 볼 지표가 열 개 가까이로
늘었는데, 그걸 전부 250ms 루프에 넣으면 초당 40개의 요청이 측정 대상 위에 얹힙니다. 그래서 빠른
루프는 `tomcat.threads.busy` 하나만 보고(초당 4개 — 01번보다 오히려 줄었습니다), 초 단위면 충분한
힙·커넥션 풀은 별도 프로세스가 5초 간격으로 맡습니다.

**JMeter 의 HTML 리포트는 만들지 않습니다.** 동시 500 · 10분이면 샘플이 60만 개라 리포트 생성이
측정보다 오래 걸립니다. 지연 백분위와 처리량은 `summarize.ps1` 이 `results.csv` 를 직접 훑어
정상 상태 구간만으로 계산합니다.

### 4.2 이번에 정한 것

| 항목 | 값 | 이 값을 고른 이유 |
| --- | --- | --- |
| 동시 사용자 | 100 / 300 / 500 | 워커 200 을 기준으로 **절반 · 초과 · 크게 초과** 세 지점을 찍는다. 100 은 01번과 같은 지점이라 두 문서를 잇는 못이 된다 |
| ramp-up | 30 / 90 / 150초 | **유입 속도를 3.33 users/s 로 고정**했다. 동시성마다 유입 속도가 다르면 세 구간을 나란히 놓을 수 없다. 100 → 30초는 01번과 같은 값이다 |
| 정상 상태 | **10분** | 커넥션 반납 누락은 60초에 보이지 않는다. 10분이면 회차당 수십 MB 이상 우상향하는 종류는 잡힌다(그 이상은 §7) |
| 집계 구간 | ramp-up 이후 정상 상태만 | ramp-up 동안은 스레드가 다 올라오지 않아 busy 가 낮게 나온다 |
| 워밍업 | 회차마다 20초 | JIT 과 커넥션 풀이 데워지기 전 구간을 섞으면 먼저 돌린 시나리오만 불리해진다 |
| 회차 사이 | **앱 재시작 + 기동 후 30초 정착 + 회차 뒤 60초 쿨다운** | 아래 별도 설명 |
| 반복 | 1회차로 9구간을 전부 돈 뒤, **500 구간 3경로를 2회차로 다시** | 재현성 확인은 "같은 조건을 연달아 두 번"이 아니라 "한 바퀴 돈 뒤 다시"여야 순서 효과까지 걸러진다 |

### 4.3 왜 회차마다 앱을 재시작하는가

**쿨다운만으로는 부족합니다.** 경로 B 와 경로 C 는 `WebClientConfig` 의 같은 빌더에서 나온
`WebClient` 를 쓰고, 그 `HttpClient.create()` 는 **JVM 전역 커넥션 풀(`HttpResources`)** 하나를
공유합니다. 경로 B 를 10분 돌린 뒤 남은 웜 커넥션을 경로 C 가 그대로 물려받으면, C 의 "커넥션 풀
시작 → 종료" 는 C 가 만든 값이 아니게 됩니다. 힙도 마찬가지로 앞 회차의 잔여물을 안고 시작합니다.

측정하려는 것이 **"시작 대비 10분 후"** 인 이상, 시작점이 회차마다 같아야 합니다. 그래서
`run-matrix.ps1` 은 회차마다 앱 컨테이너를 재시작하고 `/actuator/health` 가 UP 이 될 때까지 기다린
뒤 30초를 더 둡니다.

### 4.4 스텁 용량을 올렸다 (그리고 왜 그것이 조건을 바꾸지 않는가)

01번 측정에서 실제로 걸렸던 함정이 **스텁이 먼저 포화되는 것**이었습니다. 그때 스텁을
`--container-threads 400` · `--async-response-threads 200` 으로 띄워 동시 100 을 넘겼는데,
그 값은 동시 100 을 기준으로 잡은 것입니다.

동시 500 · 지연 500ms 의 이론적 상한은 **1000 TPS** 이고, 이 조건에서는 스텁이 500개의 연결을 동시에
붙들어야 합니다. 그래서 `--container-threads 1000` · `--async-response-threads 500` 으로 올렸습니다.

**이 변경은 측정 대상의 조건을 바꾸지 않습니다.** 앱의 워커 수도, 타임아웃도, 지연도 그대로입니다.
바뀐 것은 **관측 장비의 여유**뿐입니다. 다만 이 변경 없이 잰 500 구간 값은 앱이 아니라 스텁을 잰
값이 되므로, 조건표에 적어 둡니다.

### 4.5 동기 대조군을 HTTP/1.1 로 고정했다 — 이 측정에서 실제로 걸린 함정

**첫 시도의 동시 300 회차는 오류율 80.7% 로 나왔습니다.** 워커 점유는 p95 200(포화)인데 TPS 는
1244, 지연 p50 은 153ms 였습니다. 지연이 외부 대기 500ms 보다 짧다는 것부터 앞뒤가 맞지 않습니다 —
외부를 부르지 않고 돌아온 응답이 대부분이라는 뜻입니다.

앱 로그의 원인은 이것이었습니다.

```
org.springframework.web.client.ResourceAccessException:
    I/O error on GET request for "http://wiremock:8080/...": too many concurrent streams
Caused by: java.io.IOException: too many concurrent streams
    at jdk.internal.net.http.Http2Connection.reserveStream(...)
```

JDK `HttpClient` 의 **기본 버전은 `HTTP_2`** 이고, WireMock(Jetty)이 h2c 업그레이드를 받아 줍니다.
그래서 아무것도 지정하지 않으면 **동기 경로만 커넥션 하나에 모든 요청을 다중화**합니다. 실제로
동시 40 요청을 흘렸을 때 앱→스텁 소켓은 **1개**였고(같은 시점 워커는 43개 점유), 논블로킹 경로는
동시 60 요청에 소켓 **61개**였습니다. 동시 100 까지는 이 차이가 드러나지 않습니다. 그러나 Jetty 의
`SETTINGS_MAX_CONCURRENT_STREAMS` 기본값(128)을 넘는 순간, JDK 클라이언트는 **대기시키지 않고
즉시 예외를 던집니다.**

그러므로 그 80.7% 는 **"동기 방식은 동시 300 을 못 견딘다" 가 아니라 "JDK 클라이언트가 HTTP/2 로
붙었고 스트림 상한에 걸렸다" 입니다.** 그대로 표에 실었다면 대조군을 부당하게 불리하게 만든
숫자가 됐을 것입니다.

고친 방법은 대조군의 프로토콜을 비교 대상과 맞추는 것입니다.

```java
HttpClient.newBuilder()
        .version(HttpClient.Version.HTTP_1_1)   // 기본값 HTTP_2 를 명시적으로 내린다
        .connectTimeout(TIMEOUT)
        .build();
```

**왜 이것이 "조건을 유리하게 고른 것" 이 아닌가** — 비교 대상인 `WebClient`(Reactor Netty)도,
상용 경로가 실제로 부르는 카카오 API 도 HTTP/1.1 입니다. 대조군만 HTTP/2 로 두는 쪽이 오히려
조건을 어긋나게 하는 선택이었습니다. 이 변경 뒤의 값이 §6 의 표입니다.

## 5. 재현 절차

**필요한 것** — Docker Desktop, [Apache JMeter 5.6.3](https://jmeter.apache.org/download_jmeter.cgi),
PowerShell, 그리고 저장소 루트의 `.env`.

```powershell
# 1. 벤치 스택 기동 (기본 스택 + WireMock 스텁 오버레이)
docker compose -f docker-compose.yml -f docker-compose.bench.yml up -d --build

# 2. JMeter 위치
$env:JMETER_HOME = "C:\Users\usr\tools\apache-jmeter-5.6.3"

# 3. 스텁이 그 동시성을 견디는지 먼저 확인한다. 이게 틀리면 나머지가 전부 무의미하다.
#    동시 500 의 이론적 상한은 1000 TPS 다. 여기서 나온 값이 측정의 천장이다.
java -Xmx2g -jar "$env:JMETER_HOME\bin\ApacheJMeter.jar" -n -t perf\thread-occupancy\thread-occupancy.jmx `
    "-Jhost=localhost" "-Jport=8090" "-Jpath=/v2/local/search/address.json" `
    "-Jusers=500" "-Jrampup=15" "-Jduration=75" -l "$env:TEMP\stubcheck500.csv"

# 4. 매트릭스 12회차 (3경로 × 100/300/500 × 10분 + 500 구간 2회차)
.\perf\thread-occupancy\run-matrix.ps1
```

한 조합만 다시 돌리려면:

```powershell
.\perf\thread-occupancy\run.ps1 -Scenario reactive -Users 500 -Rampup 150 -Duration 750
```

각 회차는 `perf/thread-occupancy/results/<시나리오>-u<사용자수>-<타임스탬프>/` 에 남습니다.

| 파일 | 내용 |
| --- | --- |
| `summary.csv` | 회차 요약 — 아래 표에 옮길 값 전부 |
| `timeseries.csv` | 1분 간격 스냅샷(각 분 표시 ±15초). **추이 표의 원본** |
| `metrics.csv` · `resources.csv` | 250ms · 5초 간격 원본 샘플 |
| `results.csv` | JMeter 원본 샘플 |

진행 상황은 `results/matrix-log.csv` 에 회차마다 append 됩니다. 중간에 끊겼다면 그 파일의 마지막
index 를 보고 `-StartAt <다음 index>` 로 이어서 돌립니다.

### 6.3 무엇이 보이는가

**① 동기 경로의 한계 처리량은 계산으로 예측되고, 실측이 그것과 맞는다.**

워커가 외부 응답을 기다리는 동안 묶여 있으므로, 동기 경로의 상한은 다음으로 정해집니다.

```
한계 TPS = 워커 수 ÷ 외부 지연 = 200 ÷ 0.5초 = 400 TPS
```

실측은 동시 300에서 **398.7**, 동시 500에서 **398.6** 이었습니다. 동시성을 300에서 500으로 올려도
처리량은 그대로이고 **지연만 752ms → 1254ms 로 늘었습니다.** 늘어난 200명은 일을 더 시키는 것이
아니라 줄에 서 있을 뿐입니다.

**② 논블로킹 경로는 워커 상한에 걸리지 않는다.**

| 동시성 | A(동기) | B(논블로킹) | 이론 상한 |
| --- | --- | --- | --- |
| 100 | 198.9 TPS | 198.9 TPS | 200 TPS |
| 300 | 398.7 TPS | 596.2 TPS | 600 TPS |
| 500 | 398.6 TPS | **993.7 TPS** | 1000 TPS |

동시 100에서는 두 경로가 같습니다. **200 TPS 라는 이론 상한(동시 100 ÷ 0.5초)이 워커 200 보다
낮아, 동기 경로도 아직 여유가 있기 때문입니다.** 01번 문서가 "동시 100은 아직 어느 쪽도 한계가
아니다"라고 적은 것이 이 뜻이고, 이번 측정이 그것을 수치로 확인했습니다.

동시성이 워커 수를 넘어서는 순간 갈립니다. 동시 500에서 논블로킹은 **993.7 TPS 로 동기의 2.5배**,
지연은 **1296ms → 505ms 로 2.5배 짧습니다.** 그러면서 워커는 p95 기준 **200개에서 6개**만 씁니다.

**③ 상용 경로는 벤치 경로와 같은 대역에 있다.**

경로 C는 `KakaoGeocodeAdapter` 를 그대로 부르며, 서킷브레이커와 3초 타임아웃과 fallback 이 모두
붙어 있는 실제 코드입니다. 그런데도 세 동시성 전부에서 벤치 전용 경로 B와 사실상 같습니다
(500 구간에서 993.1 vs 993.7 TPS, 워커 p95 5 vs 6). **"그건 네가 측정용으로 짠 코드 아니냐"에 대한
답이 이 줄입니다.**

계획 단계에서 우려한 서킷 개방은 일어나지 않았습니다. 회차 직후 확인한 상태는
`state=CLOSED · slowCallRate=0.0% · slowCalls=0 · failedCalls=0` 이었습니다. 지연이 503ms 에
머물러 `slowCallDurationThreshold`(2500ms) 근처에도 가지 않았기 때문입니다.

**④ 10분 동안 누수 신호는 없었다.**

이번 측정의 두 번째 질문이 이것이었습니다. 판정 근거는 셋입니다.

- **커넥션 풀** — 아홉 구간 전부에서 시작값과 종료값이 같습니다(300 구간에서 300 → 301 처럼 1 차이가
  나는 것은 5초 샘플이 커넥션 교체 순간에 걸린 것입니다). **반환되지 않고 쌓이는 조짐이 없습니다.**
  각 값이 동시 사용자 수와 정확히 일치하는 것도 함께 봐야 합니다 — 동시 500이면 500개, 그 이상도
  이하도 아닙니다.
- **워커 점유** — 10분 내내 평평합니다. 아래 §6.4 의 추이 표에서 마지막 분이 첫 분보다 높은 구간은
  없습니다. 점유가 시간에 따라 우상향하면 그것이 누수 신호인데, 그런 구간이 없었습니다.
- **힙** — 톱니로 오르내릴 뿐 추세가 없습니다. 예를 들어 B/500 회차의 분당 값은
  458.7 → 531.9 → 571.6 → 567.8 → 510.0 → 519.4 → 483.3 → 473.7 → 521.1 → 550.1 → 546.1 MB 입니다.

**정직하게 덧붙일 두 가지가 있습니다.**

- **`jvm.gc.live.data.size` 가 일부 회차에서 0 이었습니다** (B/500 1회차 내내, C/100 의 시작 시점).
  이 지표는 old 세대 수집 직후에만 갱신되는데, 이 스택의 최대 힙이 약 12GB 라 700MB 언저리를 쓰는
  10분 부하에서는 old 세대 수집이 일어나지 않는 회차가 있습니다. **0 은 "살아 있는 객체가 없다"가
  아니라 "아직 갱신되지 않았다"는 뜻이므로 누수 판정에 쓸 수 없습니다.** 그 회차의 판정은 힙 추세와
  커넥션 풀로 했습니다. 같은 조건의 2회차에서는 값이 잡혔고 **149.5 → 149.5 로 변화가 없었습니다.**
- **JVM 스레드 수는 10분 시점에도 완만히 늘고 있었습니다** (B/500: 76 → 134). 톰캣 워커 풀이 순간
  스파이크에 맞춰 늘어난 것으로 보이고 상한은 200이지만, **이 측정으로 "평탄화된다"고 단정할 수는
  없습니다.** 확인하려면 더 긴 측정이 필요합니다.

### 6.7 이력서에 쓸 수 있는 문장

01번 문서는 이력서의 "스레드 사용률 57% 감소"를 실측값 98% 로 고쳤습니다. 이 측정은 거기에
**"그래서 무엇이 달라지는가"** 를 붙일 수 있게 합니다.

> 외부 API 대기 500ms 조건에서 동기 방식 대비 톰캣 워커 점유 p95 를 101 → 1 (사용률 50.5% → 0.5%)
> 로 낮추고, **동시 500 · 10분 지속 부하에서 처리량 398.6 → 993.7 TPS (2.5배), 지연 p95
> 1296ms → 505ms 로 개선.** 두 방식 모두 오류율 0%, 커넥션 풀·힙 증가 없음.

숫자마다 조건(외부 지연 500ms · 동시 500 · 10분 · 톰캣 워커 200)을 함께 말할 수 있어야 이 문장이
성립합니다. 조건을 뺀 "2.5배"는 01번 문서가 지적한 "57%"와 같은 종류의 문장이 됩니다.

## 7. 이 측정이 말하지 않는 것

- **로컬 Docker 환경입니다.** 오토스케일링도 로드밸런서도 없습니다. 운영에서는 ECS 태스크가 여러 개
  뜨고 그 앞에 ALB 가 섭니다([`infra/`](../../infra/)의 CDK 가 그렇게 정의합니다). 그러므로 여기서
  본 **단일 인스턴스의 포화점이 곧 서비스의 포화점은 아닙니다.** 동기 경로가 워커 200 에서 막힌다는
  것은 "태스크 하나가 그렇다"는 뜻이고, 운영에서는 태스크를 늘려 같은 트래픽을 받을 수 있습니다.
  다만 **태스크를 늘린다는 것은 돈을 쓴다는 뜻**이고, 이 측정이 보이는 것은 같은 트래픽을 받는 데
  필요한 태스크 수의 차이입니다.
- **500 · 300 · 100 은 실제 사용자 트래픽 추정치가 아닙니다.** 이 서비스가 동시 500명을 받는다는
  근거는 어디에도 없습니다. 톰캣 워커 기본값 200 을 기준으로 **절반(100) · 초과(300) · 크게
  초과(500)** 라는 세 지점을 임의로 고른 것이고, 그 이상도 이하도 아닙니다. 실제 트래픽 규모를
  말하려면 운영 로그를 근거로 다시 잡아야 합니다.
- **단일 호스트입니다.** JMeter · 앱 · WireMock · MySQL · Redis 가 6코어 12스레드 한 대를 나눠
  씁니다. 부하 도구 자신이 병목이 될 수 있어 회차마다 호스트 CPU 를 함께 기록했습니다
  (`resources.csv` 의 `hostCpuPercent`).
- **10분은 누수 판정에 넉넉한 길이가 아닙니다.** 이 길이로 잡히는 것은 회차당 수십 MB 이상
  우상향하거나 커넥션이 반납되지 않고 쌓이는 종류뿐입니다. **하루 단위로 서서히 새는 종류는
  이 측정으로 없다고 말할 수 없습니다.** "10분 동안은 늘지 않았다" 이상을 주장하지 않습니다.
- **경로 A 는 재구성한 대조군입니다.** 01번 문서 §1 에 적었듯 이 저장소에 `RestClient` 구현이
  존재한 적은 없습니다. A 는 "우리가 겪었던 과거 코드"가 아니라 **같은 조건에서 동기 방식이 어떻게
  동작하는지 보이기 위해 만든 대조군**입니다.
- **응답 시간은 외부 지연 500ms 가 지배합니다.** 논블로킹이 사용자 체감 지연을 줄여 주지는
  않습니다(01번과 동일). 이 방식이 사는 곳은 같은 워커 수로 더 많은 동시 요청을 견디는 쪽입니다.
- **DB 접근은 여전히 블로킹입니다.** 이 서버는 JPA 를 씁니다. 논블로킹으로 바뀐 것은 아웃바운드
  외부 API 대기 구간뿐이고, 이 측정도 딱 그 구간만 다룹니다. 세 경로 모두 DB 를 거치지 않으므로
  Hikari 풀이 평탄한 것은 **누수가 없다는 증거가 아니라 이 부하가 DB 를 건드리지 않았다는 뜻**입니다.
- **이벤트 루프 스레드는 워커 점유 지표에 잡히지 않습니다.** `tomcat.threads.busy` 는 워커 풀만
  봅니다. 논블로킹 경로가 반납한 부담은 `reactor-http-nio-*` 로 옮겨 가고, 그 스레드는 코어 수만큼
  밖에 없습니다. 그 그룹이 막히면 어떤 일이 벌어지는지는
  [트러블슈팅 01](../troubleshooting/01-reactive-blocking-io.md)에 있습니다.
- **힙 상한이 큽니다.** 이 스택의 앱 컨테이너는 메모리 제한이 없고 `-XX:MaxRAMPercentage=75.0` 로
  최대 힙이 약 12GB 입니다. GC 가 급할 이유가 없어 힙 used 는 크게 오르내립니다. 그래서 누수 판정은
  used 가 아니라 `jvm.gc.live.data.size`(live set)로 합니다(§2). 운영 태스크의 메모리 설정은 다르므로
  여기의 힙 절대값을 운영 값으로 읽으면 안 됩니다.
