## 1. 이 문서가 있는 이유

"스레드 사용률 57% 감소"는 **비교군이 있어야 성립하는 문장**입니다. 무엇 대비 57%인지, 무엇을 사용률이라 부르는지가 정해져야 검증할 수 있습니다.

그런데 이 저장소에는 **`RestClient` 구현이 한 줄도 없습니다.** 처음부터 `WebClient`로 짰고, 동기 클라이언트에서 옮겨 온 마이그레이션이 실제로 일어난 적이 없습니다. 원래의 숫자는 코드가
아니라 **테스트 코드 안에서 만든 상황**을 재서 나온 것이었고, 그래서 "어느 시점의 무엇과 비교한 값인가"에 답할 수 없었습니다.

그 공백을 두 가지로 메웠습니다.

- **비교군을 코드로 만들었습니다.** 같은 스텁을, 같은 타임아웃으로, 논블로킹과 동기로 각각 부르는 두 엔드포인트를 `bench` 프로파일 뒤에 두었습니다. 상용 코드를 되돌리지 않고도 A/B가 가능합니다.
- **부하와 관측을 분리했습니다.** 부하는 JMeter가 걸고, 스레드 점유는 Actuator에서 긁습니다. 부하 도구는 워커 점유를 볼 수 없기 때문입니다 (§3).

## 2. 무엇을 재는가 — 지표의 정의

이 측정에서 **"스레드 사용률"은 다음 한 가지만을 뜻합니다.**

```
스레드 사용률(%) = tomcat.threads.busy / tomcat.threads.config.max × 100
```

| 항목                        | 정의                                                                      |
|-----------------------------|---------------------------------------------------------------------------|
| `tomcat.threads.busy`       | 지금 요청을 처리 중인 톰캣 워커 스레드 수 (Actuator 기본 제공 지표)       |
| `tomcat.threads.config.max` | 톰캣 워커 풀의 상한. 이 측정에서는 스프링 부트 기본값 **200**             |
| 대표값                      | 정상 상태 구간의 **p95**. 평균과 최댓값도 함께 기록하되 비교는 p95로 한다 |
| 감소율                      | `(동기 p95 − 논블로킹 p95) / 동기 p95 × 100`                              |

**대표값으로 p95를 쓰는 이유** — 평균은 부하가 흔들린 구간에 끌려 내려가고, 최댓값은 샘플 하나가 결정합니다. 우리가 알고 싶은 것은 "이 부하에서 워커 풀이 평소 얼마나 잠겨 있는가"이므로, 한쪽 꼬리에
휘둘리지 않으면서 포화에 가까운 쪽을 보는 p95가 맞습니다.

**"CPU 사용률"이 아닙니다.** 논블로킹은 CPU를 아끼는 기법이 아니라 **대기 중인 스레드를 반납하는**
기법입니다. 이 측정이 보여 줄 수 있는 것은 워커 점유이고, 그 이상을 주장하지 않습니다.

## 3. 왜 부하 도구만으로는 못 재는가

JMeter가 아는 것은 **응답 시간과 처리량**뿐입니다. "요청 하나가 워커를 몇 초 붙잡고 있었나"는 서버 안에서만 보입니다. 그래서 관측을 둘로 나눴습니다.

| 역할             | 도구                                                        | 산출물                     |
|------------------|-------------------------------------------------------------|----------------------------|
| 부하 생성        | Apache JMeter 5.6.3 (non-GUI)                               | `results.csv`, HTML 리포트 |
| 외부 API 대역    | WireMock 3.9.1 (고정 지연 500ms)                            | —                          |
| 스레드 점유 관측 | Spring Boot Actuator `/actuator/metrics` 를 250ms 간격 폴링 | `metrics.csv`              |
| 집계             | [`run.ps1`](../../perf/thread-occupancy/run.ps1)            | `summary.csv`              |

샘플러는 JMeter와 **별도 프로세스**로 띄웁니다. 같은 프로세스에 두면 부하가 샘플링 간격을 흔들어, 정작 포화 구간의 샘플이 성기게 찍힙니다.

**`tomcat.threads.*` 는 그냥 나오지 않습니다.** Actuator를 붙이는 것만으로는 `tomcat.sessions.*`
밖에 바인딩되지 않고, 워커 점유를 보려면 Tomcat의 MBean 레지스트리가 켜져 있어야 합니다 (`server.tomcat.mbeanregistry.enabled`). 측정에만 필요한 설정이라 상용 설정이
아니라
`docker-compose.bench.yml`에 두었습니다. 이 값을 켜지 않으면 샘플러는 빈 CSV만 남깁니다.

## 4. 측정 조건

| 항목                   | 값                                                      | 이 값을 고른 이유                                                                           |
|------------------------|---------------------------------------------------------|---------------------------------------------------------------------------------------------|
| 비교군 A (동기)        | `GET /bench/blocking` — `RestClient` (JDK `HttpClient`) | 응답을 기다리는 동안 워커가 묶인다                                                          |
| 비교군 B (논블로킹)    | `GET /bench/reactive` — `WebClient` (Reactor Netty)     | `Mono` 반환 → 비동기 서블릿으로 어댑팅되어 워커를 반납한다                                  |
| 대조군 C (상용 경로)   | `GET /api/v1/geocode` — `KakaoGeocodeAdapter`           | 합성 엔드포인트만으로는 "그건 벤치 코드지 앱이 아니다"라는 반박을 받는다                    |
| 외부 응답 지연         | **고정 500ms**                                          | 아래 별도 설명                                                                              |
| 톰캣 `max-threads`     | **200 (스프링 부트 기본값)**                            | 아래 별도 설명                                                                              |
| 동시 사용자            | 100 (기본)                                              | 200스레드 풀을 동기 경로가 절반쯤 잠그는 지점. 필요하면 `-Users` 로 바꿔 여러 지점을 찍는다 |
| ramp-up                | 30초                                                    | 100개 스레드가 한꺼번에 붙으면 첫 몇 초의 큐잉이 정상 상태처럼 보인다                       |
| 총 수행 시간           | 90초 (ramp-up 30 + 정상 상태 60)                        | 정상 상태 60초 × 250ms = 약 240 샘플                                                        |
| 워밍업                 | 측정 전 20초                                            | JIT과 커넥션 풀이 데워지기 전 구간을 섞으면 **먼저 돌린 시나리오만 불리해진다**             |
| 집계 구간              | ramp-up 이후 정상 상태만                                | ramp-up 동안은 스레드가 다 올라오지 않아 busy가 낮게 나온다                                 |
| Keep-Alive             | 켬                                                      | 매 요청 TCP 핸드셰이크를 하면 측정 대상이 커넥션 수립 비용으로 바뀐다                       |
| 응답 검증              | HTTP 200 assertion                                      | 타임아웃으로 조기 반납된 요청이 "빠른 응답"으로 집계되는 것을 막는다                        |
| 두 클라이언트 타임아웃 | 양쪽 모두 연결·응답 **5초**                             | 한쪽만 타임아웃이 짧으면 그 차이가 스레드 수로 둔갑한다                                     |

### 왜 외부 지연을 500ms 고정으로 두는가

논블로킹의 이득은 **대기 시간에 비례**합니다. 지연이 0에 가까우면 두 방식의 차이도 0에 가까워지고, 지연을 몇 초로 키우면 원하는 만큼 큰 숫자를 만들 수 있습니다. **숫자를 고를 수 있다는 것 자체가
측정의 결함**입니다.

500ms는 임의로 고른 값이 아니라 **이 서버가 실제로 부르는 외부 API의 응답 시간대**입니다 (카카오 지오코딩). 값을 바꿔 여러 지점을 찍는 것은 환영하지만, 그때는 **표에 지연값을 함께 적어야**
합니다. 지연을 밝히지 않은 스레드 점유 수치는 아무것도 말하지 않습니다.

### 왜 톰캣 워커 수를 기본값 200 그대로 두는가

워커 수를 줄이면 동기 경로가 훨씬 빨리 포화되어 **차이가 극적으로 커집니다.** 그렇게 만든 숫자는
"설정을 유리하게 골랐다"는 반박을 그대로 받습니다. 운영에서 쓰는 값을 그대로 두는 쪽이, 숫자는 작아져도 방어할 수 있는 숫자입니다.

### 부하 도구와 스텁이 먼저 포화되면 안 된다

**이 측정에서 실제로 처음 걸린 함정입니다.** 첫 회차는 세 시나리오가 모두 TPS 37에서 멈추고 오류율이 23~99%로 나왔습니다. 앱이 느린 것이 아니라 **스텁이 먼저 죽은 것**이었습니다.
WireMock은 기본 설정에서 지연 응답 하나가 컨테이너 스레드 하나를 그대로 붙잡습니다. 500ms × 동시 100이면 스텁 쪽이 먼저 포화되고, 그 뒤로는 무엇을 재든 스텁의 대기 시간을 재게 됩니다.

그래서 스텁을 `--async-response-enabled`(지연 응답을 스케줄러로 넘김) + `--async-response-threads 200`

+ `--container-threads 400`으로 띄우고, **측정 전에 스텁 단독 처리량을 먼저 확인합니다.**

```powershell
# 앱을 거치지 않고 스텁만 때려 본다. 여기서 나온 TPS 가 측정의 천장이다.
java -jar "$env:JMETER_HOME\bin\ApacheJMeter.jar" -n -t perf\thread-occupancy\thread-occupancy.jmx `
    "-Jhost=localhost" "-Jport=8090" "-Jpath=/v2/local/search/address.json" `
    "-Jusers=100" "-Jrampup=5" "-Jduration=35" -l "$env:TEMP\stubcheck.csv"
```

동시 100 · 500ms의 이론적 상한은 200 TPS이고, 고친 뒤 스텁은 **184 TPS · 오류 0% · 평균 501ms**를 냈습니다. 이 확인을 건너뛴 측정은 앱이 아니라 스텁을 잰 것일 수 있습니다.

### 왜 상용 엔드포인트까지 같은 스텁을 보게 하는가

`docker-compose.bench.yml`은 `KAKAO_GEOCODING_DAPI`를 스텁으로 덮어써, **상용 지오코딩 어댑터도 같은 500ms 스텁**을 부르게 만듭니다. 벤치 전용 엔드포인트만 재면
"그건 네가 측정용으로 짠 코드 아니냐"는 물음에 답할 수 없습니다. 세 경로가 **같은 외부 조건**에 놓여야, 상용 경로 C의 값이 논블로킹 B와 같은 대역에 있다는 것을 보일 수 있습니다.

## 5. 재현 절차

**필요한 것** — Docker Desktop, [Apache JMeter 5.6.3](https://jmeter.apache.org/download_jmeter.cgi), PowerShell, 그리고 저장소
루트의 `.env`.

```powershell
# 1. 벤치 스택 기동 (기본 스택 + WireMock 스텁 오버레이)
docker compose -f docker-compose.yml -f docker-compose.bench.yml up -d --build

# 2. 스텁이 정말 500ms 걸리는지, 그리고 부하를 견디는지 먼저 확인한다.
#    이게 틀리면 나머지가 전부 무의미하다 (§4의 "부하 도구와 스텁이 먼저 포화되면 안 된다").
Measure-Command { Invoke-WebRequest "http://localhost:8090/v2/local/search/address.json" -UseBasicParsing }

# 3. JMeter 위치를 알려 준다
$env:JMETER_HOME = "C:\apache-jmeter-5.6.3"

# 4. 세 시나리오를 같은 조건으로 한 번씩 돌린다
.\perf\thread-occupancy\run.ps1 -Scenario blocking -Users 100
.\perf\thread-occupancy\run.ps1 -Scenario reactive -Users 100
.\perf\thread-occupancy\run.ps1 -Scenario geocode  -Users 100
```

각 회차는 `perf/thread-occupancy/results/<시나리오>-u<사용자수>-<타임스탬프>/` 에 남습니다.

| 파일                                | 내용                                                                       |
|-------------------------------------|----------------------------------------------------------------------------|
| `summary.csv`                       | `busyMean` · `busyP95` · `busyPeak` · `utilP95Percent` — 아래 표에 옮길 값 |
| `metrics.csv`                       | 250ms 간격 원본 샘플. 그래프를 그리거나 이상 구간을 되짚을 때              |
| `results.csv` · `report/index.html` | JMeter의 응답 시간·처리량·오류율                                           |

**시나리오 순서를 바꿔 한 번 더 돌려 보길 권합니다.** 순서를 바꿔도 결론이 같아야 워밍업이 제대로 먹었다는 뜻입니다.

## 6. 측정 결과

WireMock 3.9.1 · 동시 사용자 100 · 정상 상태 샘플 241~243개

| 시나리오             | 클라이언트                | busy 평균 | busy p95 | busy 최대 | 사용률 p95 (/200) |
|----------------------|---------------------------|-----------|----------|-----------|-------------------|
| A. `/bench/blocking` | `RestClient` (동기)       | 96.20     | **101**  | 101       | **50.5%**         |
| B. `/bench/reactive` | `WebClient` (논블로킹)    | 1.27      | **2**    | 9         | **1.0%**          |
| C. `/api/v1/geocode` | 상용 어댑터 (`WebClient`) | 1.28      | 3        | 9         | 1.5%              |

**감소율** = (101 − 2) / 101 × 100 = **98.0%** (평균 기준으로는 (96.20 − 1.27) / 96.20 = 98.7%)

**같은 조건이었음을 보이는 숫자** — 스레드만 줄고 처리량이 함께 떨어졌다면 그것은 개선이 아니라 **다른 곳으로 옮긴 병목**입니다. 세 시나리오의 처리량과 지연이 사실상 동일하다는 것이 위 감소율에 의미를
줍니다.

| 시나리오             | 요청 수 | 오류율    | 처리량    | 평균 응답 | p95 응답 |
|----------------------|---------|-----------|-----------|-----------|----------|
| A. `/bench/blocking` | 14,987  | **0.00%** | 165.8 TPS | 503ms     | 504ms    |
| B. `/bench/reactive` | 14,985  | **0.00%** | 165.8 TPS | 503ms     | 504ms    |
| C. `/api/v1/geocode` | 14,979  | **0.00%** | 165.7 TPS | 503ms     | 504ms    |

**정상 상태 구간의 시간 프로파일** (10초 구간별 `busy` 평균)

| 경과         | 0s   | 10s  | 20s  | 30s   | 40s   | 50s   | 60s   | 70s   | 80s   |
|--------------|------|------|------|-------|-------|-------|-------|-------|-------|
| A. 동기      | 16.3 | 49.6 | 82.9 | 100.5 | 100.8 | 100.6 | 100.9 | 100.3 | 100.4 |
| B. 논블로킹  | 1.1  | 1.3  | 1.0  | 1.8   | 1.3   | 1.0   | 1.2   | 1.3   | 1.2   |
| C. 상용 경로 | 1.2  | 1.1  | 1.2  | 1.7   | 1.2   | 1.3   | 1.2   | 1.0   | 1.4   |

동기 경로는 ramp-up 30초 동안 워커를 그대로 쌓아 올린 뒤 **100 근처에서 평평해집니다.**
동시 사용자 100명이 각자 워커를 하나씩 붙잡고 있는 모습이고, 샘플이 이따금 101을 찍는 것은 Actuator를 긁는 샘플러 자신의 요청이 겹쳤기 때문입니다. 논블로킹 경로와 상용 경로는 같은 부하에서
**처음부터 끝까지 1 언저리**입니다 — 워커는 외부 응답을 기다리지 않고 곧바로 반납됩니다.

### 이력서 문구는 이 값으로 고쳐야 합니다

이력서의 **"스레드 사용률 57% 감소"**는 이 하네스가 낸 값이 아닙니다. 같은 조건에서 실제로 측정한 값은 **98%**이며, 정확히 말하면 *"외부 API 대기 500ms · 동시 100 요청에서 톰캣 워커
점유 p95가 101에서 2로, 사용률로는 50.5%에서 1.0%로 감소"*입니다. 숫자를 낮춰 잡을 이유도, 근거 없는 숫자를 유지할 이유도 없습니다.

## 7. 이 측정이 말하지 않는 것

- **응답 시간은 거의 같습니다.** 외부 지연 500ms가 지배적이라, 논블로킹이 사용자 체감 지연을 줄여 주지는 않습니다. 이 방식이 사는 곳은 **같은 워커 수로 더 많은 동시 요청을 견디는** 쪽입니다.
- **이벤트 루프 스레드는 이 지표에 잡히지 않습니다.** `tomcat.threads.busy`는 워커 풀만 봅니다. 논블로킹 경로가 반납한 부담은 `reactor-http-nio-*` 로 옮겨 가고, 그
  스레드는 코어 수만큼밖에 없습니다. 그 그룹이 막히면 어떤 일이 벌어지는지는
  [트러블슈팅 01](../troubleshooting/01-reactive-blocking-io.md)에 있습니다.
- **DB 접근은 여전히 블로킹입니다.** 이 서버는 JPA를 씁니다. 논블로킹으로 바뀐 것은 **아웃바운드 외부 API 대기 구간뿐**이고, 이 측정도 딱 그 구간만 다룹니다.
- **단일 호스트 측정입니다.** JMeter와 앱과 스텁이 한 머신에 있어, 아주 높은 동시성에서는 부하 도구 자신이 병목이 됩니다. 사용자 수를 크게 올릴 때는 JMeter 쪽 CPU도 함께 기록해야 합니다.
- **동시 100은 아직 어느 쪽도 한계가 아닙니다.** 동기 경로는 워커 200 중 101을 썼을 뿐이고, 아웃바운드 커넥션 풀도 여유가 있었습니다 (상용 커넥터를 그대로 쓰는 C를 동시 250으로 올려도 413
  TPS · 평균 502ms · 오류 0%). 이 측정이 보이는 것은 **같은 처리량을 내는 데 워커를 얼마나 쓰는가**이지, 각 방식의 한계 처리량이 아닙니다. 후자를 알려면 사용자 수를 올려 가며 포화점을
  찾아야 하고, 그건 별도 측정입니다.
- **비교군은 재구성한 것입니다.** §1에 적었듯 `RestClient` 구현이 이 저장소에 존재한 적은 없습니다. A는 "우리가 겪었던 과거 코드"가 아니라 **같은 조건에서 동기 방식이 어떻게 동작하는지
  보이기 위해 만든 대조군**입니다. 이 사실을 감추지 않는 편이, 감췄다가 들키는 것보다 낫습니다.
